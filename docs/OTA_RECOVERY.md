# OTA 中断恢复修复

修复日期：2026-10-13。原修复 `087f0b9` 已于 2026-10-15 纳入 [2.3.2-rc.4 公开预发布](https://github.com/xiongzai666/jcalendar-plus/releases/tag/v2.3.2-rc.4)，发行来源 `394e47b`；2.3.2-rc.3 附件保持其原始来源。以下实机记录仍对应修复当时的验证窗口。

## 改动与原因

SDK 的 `WiFiClient::connected()` 可能在对方发送 TCP FIN 后仍返回真；原表单尾部使用多次一秒超时的字符串读取。现有受限字节读取增加非消费 FIN 探测，尾部逐字节核对完整的 CR/LF，断开时立即执行上传中止。固件仍只在完整请求结束后激活。探测保存并恢复 errno，避免 SDK 下一连接判断受到前一 socket 错误污染；识别连接重置并立即中止。

主机真实 TCP 半关闭回归先失败（虚拟计时 8000 ms），修复后为 0 ms；正常上传、分段尾部、中途断开、停发超时、截断终止符、配置表单和实际 OTA 回调通过。完整 Z15 生产固件构建成功：1845584 字节，SHA256 `d53f5bf1924bea8076c0734ae1557abac98d28057a92f889c19764974143bfd7`。SDK 原有 VLA 编译警告保留。

## 实机与测量边界

发送端将数据交给操作系统不等于设备已完成写入。阶段日志实测整份上传处理约 13.18 秒，文件结束至中止约 1 毫秒；前几轮紧邻请求超时／重置发生在设备仍处理缓冲数据时，失败原件保留。改变 Windows 发送缓冲大小没有解决此测量问题。定速旧代码也在 0.141 秒内正常恢复，因此旧边界不能全部归因于清理故障。首候选新增探测未保护 errno，实机仍重置；回归移除错误码保护会失败，恢复后通过，新候选实机也通过。各次失败均保留。

最终采用每 1436 字节间隔 20 ms 的定速发送，发送速度低于实测写入速度；停止后沿用原有 200 ms 间隔立即 GET。没有增加中止后的五秒等待，也没有因失败自动重传 OTA。

- 同条件旧入口首次请求：{"httpStatus": 200, "seconds": 0.141, "value": {"validation": true, "phase": "baseline", "bootAddress": 65536, "runningAddress": 65536, "uptime": 29786, "heap": 205924, "largest": 110580}}。
- 修复后文件结束、缺最终尾部并关闭发送：HTTP 200，0.125 秒。
- 修复后写入中途断开：HTTP 200，0.375 秒。
- 后续错驱动 HTTP 400，最终 GET 200；实测 boot/running 地址均保持 `0x10000`，没有误激活。

设备已恢复当前 2.5.9 和最新配置；启动前两个应用与四个数据分区全部匹配实时备份，整片设备 MD5 `a891b35b0d76ff17997b2b65bb27770e` 一致，联网及屏幕刷新成功，零 panic／brownout。

同步 HTTP 服务在处理仍未消费的上传数据时仍会忙碌；本次验收证明已中止后的恢复，不承诺上传进行中同时响应其他请求。其他型号和全天／功耗不追加实测。
