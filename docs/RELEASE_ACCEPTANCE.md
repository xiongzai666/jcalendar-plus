## 2.3.2-rc.1：本机 OTA 输入与激活边界

WiFiManager 2.0.17 原上传回调在文件开始时调用 Update，不检查驱动。本项目通过其建服回调先注册 `/u`；已核对当前 WebServer 将处理器追加至链尾并使用首个匹配，因此实际上传进入项目的校验路径。

前次草稿的两个缺口已在本轮复现并处理：SDK 与草稿同时定义 `esp_app_desc` 导致链接失败；`UPLOAD_FILE_END` 早于整个 multipart 请求完成，在此处激活会让随后中断的请求留下新启动分区。现在沿用 [ESP-IDF 标准自定义描述位置](https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32/api-reference/system/app_image_format.html)，在 SDK 描述后写入驱动名及版本；仅在请求完成回调调用 Update 最终校验并激活。

Z15 完整构建通过。应用镜像为 1,855,984 字节，SHA256 `cfd419478b3e55409ff1d7b3892f7e61379d79b23ee5da042d5eaefae4e54964`，占应用分区约 94.4%。真实生成镜像已通过生产 Guard 的分块输入检查。主机回归运行实际 `src/local_ota.cpp`，仅替换 HTTP／Flash／重启外部边界，覆盖正常包、错驱动、短文件、文件边界后中断及一请求两个文件；提前激活回归先失败后通过。发布包相关 6 项测试通过。

Z15 已完成本机真实 HTTP 定向检查：修改自定义驱动身份的镜像返回 400；中断后启动选择仍为 app0／seq1，非活动分区启动头仍擦除；有效请求返回 200，Flash 核得 app1／seq2，应用 SHA 与上述候选一致。没有重发上传。

配置页已有字段在中断前与有效上传前保持一致。NVS 页、条目与数据 CRC 通过，观察到的热点密码、页面选择、天气缓存及 3 个诊断状态键保持；离线失败计数 `RC_ERR_COUNT` 从 35 增至 38，系统热点记录也变化。首次「整个 NVS 原始字节完全相同」断言失败，失败记录保留；本次未声称 NVS 原始字节一致或覆盖此前 RC2 的 23 项配置矩阵。

中断后配置页读取曾超时，当时 COM4 不可见；用户重接 USB 后只读核对启动选择通过。该窗口不能证明 HTTP 服务中断后的响应与资源回收，仍保留此未验范围。原有正常首配／离线与配置矩阵复用 RC2 证据，其他型号未作新构建或实测。旧版无驱动身份的升级／回退方式见 [刷机指南](FLASHING.md)。

## RC2：空网络配置首屏修复

RC1 的 Z15 空 NVS/SPIFFS 受控首启实际显示「时间待同步／暂时无法连接 Wi-Fi／周课表和待办仍可查看／短按上下键切换页面」，不满足 A01 的待配置首屏要求。这是实际失败，不能用已有说明文档抵消。

RC2 在既有联网尝试初始化 STA 后、关闭 Wi-Fi 前，以零初始化 `wifi_config_t` 和检查返回值的 `esp_wifi_get_config` 读取主 SSID，同时只读备用 SSID。已联网、任意已保存 SSID 或任一读取失败均不判为首次；只有两项明确为空才显示「设备待配置」，提示长按上键 5 秒后松开、连接 J-Calendar 热点、打开 192.168.4.1，密码见设备配置页面。不自动开热点、不改用户配置或采集策略。

已核对 WiFiManager 2.0.17：`getWiFiIsSaved()` 等价于持久 SSID 非空，但 ESP32 实现未检查 `esp_wifi_get_config` 返回且未零初始化，因此这里采用项目已有的 ESP32 API 并显式保留未知状态。主机回归执行实际 `setup()` 网络尾段、只读判定和 `task_screen()`；仅替换硬件接口，沿用固定 U8g2 1.8.0 的真实字体和解码器。首配文字宽度分别为 79、151、144、129、107 像素，真实字形绘制均在 400 × 300 内。RC2 空 NVS 的实屏、热点、保存及真实 OTA 已完成Z15受控验收，详见下方实机记录；不据此推断其他型号。

## 真实云端编译产物

`npm run build` 仍是静态和语法检查。发布前额外执行实际编译验收：

```sh
npm ci --prefix remote
# 安装或指定固定版本 EdgeOne CLI 1.6.41 的 edgeone-bin/edgeone.js
export EDGEONE_CLI_ENTRY=/absolute/path/node_modules/edgeone/edgeone-bin/edgeone.js
npm run build:candidate --prefix remote
```

Windows 可用 PowerShell 设置 `$env:EDGEONE_CLI_ENTRY`。脚本使用当前 Node 的目录执行子进程 npm；海外依赖默认经 `http://127.0.0.1:7897`，loopback 不代理。无本地代理的环境显式设置空 `HTTP_PROXY` 和 `HTTPS_PROXY`。

输出位于忽略的 `.releases/public-candidates/edgeone-*`：`receipt.json`、`artifact.zip`、`build.log` 和清洁源码/编译快照。收据包含来源提交、是否存在未提交改动、源文件散列、Node/CLI/Blob SDK 版本、编译产物散列和 ZIP SHA。源码变动或增删文件会拒绝签发候选；ZIP 改动会拒绝散列验证。

脚本不读取工程 `.env`，不继承服务认证变量、不复制设备数据、不上传。该 ZIP 的收据明确 `fixtureOnly: true`、`deployable: false`，仅供编译验收，不能直接替代带自己生产配置的正式部署。格式为 CLI 所需的 `remote/.edgeone/*` 与 `remote/edgeone.json`。

验收运行完整 CLI server entry，包含 Node 路由包装与真实 `@edgeone/pages-blob` SDK。仅 HTTP 监听与 Blob 传输被隔离到本地内存 fixture，其他网络请求禁止。依次验证登录、未授权拒绝、保存/存储、旧 revision 冲突、最多六条待办投影、已完成项排除、schema 1/2 与 426、设备确认、状态与历史权限、历史恢复产生新 revision 且旧版本保留。此证据没有覆盖平台实际 Blob 服务、预览域名、跨进程一致性或分布式写入。

## 固件构建与包

```sh
python -m pip install platformio==6.2.0
python tools/verify.py --environment z15
# 先提交已验证源码，工程必须干净；runner执行四驱动并记录输入/输出SHA
python tools/build_firmware.py
# Windows中文路径可为上一步传入 --project-dir ASCII_JUNCTION
# boot_app0路径来自本机已安装框架
python tools/release_bundle.py --boot-app0 /path/to/framework-arduinoespressif32/tools/partitions/boot_app0.bin
```

各包仅包含 bootloader、partitions、boot_app0、firmware、刷写说明、manifest 和 SHA256SUMS。打包会拒绝缺少或超大段，以及 app0/app1 地址或容量不符的分区表。两应用分区均 `0x1e0000`（1,966,080 字节）；manifest 的 `ota.imageFraction` 是应用文件占比，`deviceUpgradeVerified: false` 表示签包时 OTA 尚未实测；冻结manifest不改写，后续Z15实测在下方单独追加。

runner 在提交后的同一工作树构建四驱动，核对构建前后的固件源码输入与 HEAD，并生成 `.pio/build/build-receipt.json`。打包必须同时匹配该收据的提交、当前 include/src/lib/PlatformIO 配置散列与各段内容，拒绝把旧二进制署名为新 HEAD。全套 `verify.py` 可先构建/验证未提交修复；最终收据则要求提交后重新执行 runner。

本轮 Windows 链接器在包含中文的工程路径为 `1680` 写入 `firmware.map` 时返回 `Invalid argument`，不能算四驱动通过。修复方式是创建指向同一隔离工作树的临时 ASCII junction，再使用 `platformio run --project-dir ASCII_PATH` 构建；没有复制或覆盖其他工程。最终门禁要求四驱动均成功，仍失败则停止签发该驱动包。Linux CI 不需要这个路径别名。

依赖收据保留 `.piopm` 的解析名称、版本、来源与元数据 SHA，PlatformIO 配置散列和检入库逐文件 SHA。默认 PlatformIO home 为 `~/.platformio`，可指定 `--platformio-home`。工具收据仅选取本项目的 espressif32 平台、Arduino 框架、ESP32 工具链与 esptool，库收据仅选取该驱动目录，使用范围同时核对构建日志中的依赖图。当前直接依赖固定版本/提交，GFX 和 BusIO 等传递依赖仍需结合收据复现，不能声称完整锁定所有上游解析。
